# Versioning workflow

This project uses [Semantic Versioning 2.0](https://semver.org/) with
[Conventional Commits](https://www.conventionalcommits.org/) and an
automated CHANGELOG generated by [git-cliff](https://git-cliff.org/).

## SemVer summary

`MAJOR.MINOR.PATCH`

- **MAJOR** — incompatible API / behavior change.
- **MINOR** — backwards-compatible feature.
- **PATCH** — backwards-compatible bug fix.

While we are in `0.x`, anything MAY break between minor versions —
documented loudly in `CHANGELOG.md`. We commit to SemVer rigor at `1.0.0`.

Pre-release suffixes (used for M2 public beta and M3 RCs):

- `0.9.0-alpha.1` ← early adopters, expect breakage.
- `0.9.0-beta.3` ← feature-complete, polish phase.
- `1.0.0-rc.2` ← release candidate, only critical fixes accepted.

## Release stages and version numbers

| Stage                     | Version range  | Audience              |
|---------------------------|----------------|-----------------------|
| Early alpha (current)     | `0.1.x`        | testers               |
| Public beta (M2)          | `0.9.x-beta.N` | open signup           |
| 1.0 GA (M3)               | `1.0.0`        | everyone              |

## Workflow — adding a change

1. Make the change on a branch.
2. Commit using Conventional Commits — see [`CONTRIBUTING.md`](../CONTRIBUTING.md).
3. (User-visible only) — add a line to `CHANGELOG.md` under `## [Unreleased]`.
4. Open a PR ; squash-merge with a clean Conventional Commit subject.

## Workflow — cutting a release

```bash
# 1. Confirm CHANGELOG.md [Unreleased] is curated.
$EDITOR CHANGELOG.md

# 2. Pick the version — let cargo-release decide based on commit types.
#    Patch bump:
cargo release patch --workspace --no-publish --no-push
#    Minor bump:
cargo release minor --workspace --no-publish --no-push
#    Major bump:
cargo release major --workspace --no-publish --no-push

# `cargo release` updates Cargo.toml(s), creates the tag, and commits.

# 3. Regenerate CHANGELOG.md from the tag history (fills the new section
#    with the auto-curated commit list; merge with the hand-written prose).
git cliff --tag v$(cargo metadata --no-deps --format-version 1 \
    | jq -r '.packages[] | select(.name == "brouillon") | .version') \
    -o CHANGELOG.md
$EDITOR CHANGELOG.md   # hand-edit narrative entries

# 4. Amend the release commit with the regenerated CHANGELOG and push the tag.
git add CHANGELOG.md
git commit --amend --no-edit
git push --follow-tags
```

`cargo-dist` is configured to fire on every annotated tag matching `v*` —
GitHub Actions matrix produces signed builds for Win + Mac + Linux and
attaches them to the GitHub Release.

## Workflow — emergency hotfix

```bash
git switch -c hotfix/<short-name> v<last-released>
# … fix …
git commit -m "fix(<scope>): <subject>"
cargo release patch --workspace --no-publish --no-push
git push --follow-tags
```

The release pipeline picks it up automatically.

## Branch policy

- `main` — always green, always releasable.
- `next` — optional integration branch for features targeting the next MINOR.
- `hotfix/*` — short-lived, merge back to `main` then to `next`.

## Tagging policy

- Annotated tags only (`git tag -a v0.1.0 -m "…"`). `cargo-release` does this.
- Tag name matches the version: `v0.1.0`, `v0.9.0-beta.1`, `v1.0.0-rc.1`.
- Tag message includes one paragraph of release narrative.

## CHANGELOG curation

`git cliff` auto-generates the *list* of commits per release section.
The maintainer edits each section by hand to:
- Group related commits.
- Add a one-paragraph release narrative at the top.
- Highlight breaking changes loudly.
- Add migration notes for breaking changes.

Per Keep-a-Changelog, every release has these sections (in this order, omit if empty):

1. **Added**
2. **Changed**
3. **Deprecated**
4. **Removed**
5. **Fixed**
6. **Security**
7. **Performance** (project-local extension — we care about perf headlines)
8. **Documentation** (project-local extension — docs-only entries grouped)
9. **Internal** (chore/build/ci — least interesting, ship last)

## What gets bumped

- The root `CHANGELOG.md` — single source of truth.
- The PoC crate `Cargo.toml` `version = "..."` — bumped by `cargo-release`.
- Future workspace crates — bumped together (workspace versioning policy below).

## Workspace versioning policy

Until M1, every workspace crate moves in lockstep with the top-level version.
After M1, we may split:

- `core` / `editor-engine` may version independently if they become library-shaped.
- `ui` / `app-*` always lockstep with the top-level (they're the product surface).
- Plugins live in their own repos with independent versions.
